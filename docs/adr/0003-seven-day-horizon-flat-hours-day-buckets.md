# Forecast extends to 7 days; hours stay flat, evaluation is day-bucketed

The forecast horizon extends from **24 to 168 hourly entries** (a 7-day rolling window). The wire contract keeps **hours flat**: `hours[]` is 168 entries addressed by `index` 0..167 against `forecastStart`. "Day" is **derived** (`floor(index / 24)` → `dayIndex` 0..6), never a nested object. The decision engine searches **per day**: each activity result becomes up to 7 day-results `{ dayIndex, rating, startIndex, endIndex, duration }` (or `rating: null` for a day with no qualifying window).

Chosen because extending the horizon unlocks the multi-day timeline drill-down (users want to check tomorrow / the week, not only react to push). But the existing single-best-window search assumed a 24-hour bucket: run unchanged over 168 hours and it fuses a Thursday-evening and Friday-morning block into a "30-hour Perfect window" no human treats as one outing, and it returns windows days away when the dashboard card wants *today*. Per-day bucketing maps to how people actually plan an outing and hands the timeline view its data for free.

The window is **rolling** — every request is a fresh day 0..6 relative to `forecastStart`; there is no accumulating day counter ("day 299" never arises). Any absolute calendar position is the **derived date** (`forecastStart + index → 2026-06-22`), never a day number.

Rejected alternatives: a nested `week { days: [...] }` object (carries no payload of its own — a box around seven boxes — and hardens a grouping the client may want to slice differently, e.g. "next 48 hours" spanning two days); an unbounded single-window search over all 168 hours (produces the non-physical cross-midnight windows above).

**Consequences:** the response is a versioned contract bump — `hours[]` 24→168, `index` 0..167; the iOS decoder must not assume 24, and window indices can point a week out. The day-bucketed activity result is a new shape (replaces the single top-level window per activity). The **Daily Digest** must day-scope — slice day 0 out of 168 before searching, or a Monday push reports Saturday's window; **Window Watch** (time-ranged) is unaffected. The engine core is **untouched** — `findLongestWindow` already iterates `ratings.length`; the change is a `FORECAST_HOURS` constant replacing `slice(0, 24)` in `parse.js` plus test-fixture churn (~15 fixtures, ~6 assertions hardcode `24`/`0..23`). Payload grows ~7× (further once air-quality + marine fields land), raising the value of the 30-minute location cache. The day-bucketed engine output keeps the activity-agnostic contract of [ADR-0002](0002-activity-agnostic-engine.md) — the engine still evaluates caller-supplied profiles; only its result shape gains the day dimension.

**⚠️ Provider verification required before this is final.** Many weather providers serve hourly resolution only for the first 48–72 hours, then drop to 3-hourly or daily. Confirm Meteosource (and the air-quality / marine sources being wired pre-launch) return clean *hourly* data across all 7 days against a live response. If they degrade, the week view is coarser than the dashboard and the "168 clean hourly entries" assumption is wrong.

Recorded because clients decode against the 168-entry, day-bucketed shape (reversible only with another contract bump), a future reader will ask why hours are flat on the wire but results are bucketed and why there is no week object, and it is the result of a real trade-off between flat-vs-bucketed search and nested-vs-derived grouping.
