# Forecast extends to 7 days; hours stay flat, evaluation is day-bucketed

The forecast horizon extends from 24 hours to a **7-day rolling window**, served as a flat `hours[]` addressed by `index` against `forecastStart`. **168 (7 × 24) is a ceiling, not a fixed count.** The horizon is **provider-determined**: `hours[]` carries however many clean hourly entries the provider actually returns, capped at 168 — fewer is valid. (Verified: Meteosource's `flexi` tier returns ~164 clean hourly entries; see verification note below.) The wire contract keeps **hours flat**: no nested day object. "Day" means a **calendar day in the forecast location's local timezone** — *not* a fixed 24-hour block from `forecastStart` (the original `floor(index / 24)` rule is superseded; see "calendar bucketing" below). `dayIndex` is the **0-based ordinal of each distinct local calendar day** the horizon touches: `dayIndex 0` = today (local), `1` = tomorrow, … running `0..6` **or `0..7`**. Because the horizon starts and ends mid-day in local time, **both day 0 (today) and the final day may be partial**, so `days.length` is **not** derivable from `hours.length` alone — it depends on `forecastStart`'s *local* hour (worked example below). The decision engine searches **per local day**: each activity result becomes one day-result per bucket `{ dayIndex, rating, startIndex, endIndex, duration }` (or `rating: null` for a day with no qualifying window), where `startIndex`/`endIndex` stay **global indices into `hours[]`** — the engine searches a day's hour-slice and offsets the slice-relative result back to global before it reaches the wire. The engine is **count-agnostic** — it searches whatever hours each bucket contains — so partial days (today and the tail) need no special handling. The system **never fabricates or interpolates** hours to reach a target count; that would resurrect the false-**Perfect** hazard the absent-data guard exists to prevent.

**Calendar bucketing — how "day" is resolved.** The location's IANA timezone is supplied by the **weather provider** (Meteosource returns it as a top-level `timezone` field, e.g. `Asia/Dubai`) and normalised at the **adapter boundary** like every other field — no hardcoded offset, no geo-lookup library, DST-correct for any country via a real zone name. A small **time-boundary module** (a sibling of the adapter in the deep-module/narrow-interface sense) tags each hour with an internal `localDay` key; the engine groups by that key and never itself reasons about timezones. Bucketing by *location* tz (not the user's device tz) is deliberate: "when is the weather good **at this place**" is a location-local question, and a client-side location-shift guardrail keeps the user's active location aligned with where they are.

**Worked example (real probe numbers).** Meteosource `flexi` returned 164 hourly entries starting `2026-06-19T12:00:00Z` = `16:00` in `Asia/Dubai`. Bucketed by local calendar day: **day 0** = 16:00→23:00 local = 8 hours (indices 0–7, *partial — today*); **days 1–6** = 24 h each = 144 hours (indices 8–151); **day 7** = 00:00→11:00 local = 12 hours (indices 152–163, *partial — tail*). Total: **8 buckets** from 164 hours. The naive `floor((164-1)/24)+1` = 7 is wrong by one — which is exactly why the count is not a closed form over `hours.length`.

Chosen because extending the horizon unlocks the multi-day timeline drill-down (users want to check tomorrow / the week, not only react to push). But the existing single-best-window search assumed a 24-hour bucket: run unchanged over 168 hours and it fuses a Thursday-evening and Friday-morning block into a "30-hour Perfect window" no human treats as one outing, and it returns windows days away when the dashboard card wants *today*. Per-day bucketing maps to how people actually plan an outing and hands the timeline view its data for free. Crucially, the anti-fusion goal is only truly met when the boundaries are **local midnights**: a 24h-from-`forecastStart` block would still fuse tonight with tomorrow dawn into one window, whereas a local-calendar-day boundary separates "tonight" from "tomorrow morning" the way a person does.

The window is **rolling** — every request is a fresh day 0..N (N is 6 or 7) relative to the local date of `forecastStart`; there is no accumulating day counter ("day 299" never arises). Any absolute calendar position is the **derived date** (the local calendar date of `dayIndex`, e.g. `2026-06-22`), never a day number.

Rejected alternatives: a nested `week { days: [...] }` object (carries no payload of its own — a box around seven boxes — and hardens a grouping the client may want to slice differently, e.g. "next 48 hours" spanning two days); an unbounded single-window search over all 168 hours (produces the non-physical cross-midnight windows above).

**Consequences:** the response is a versioned contract bump — `hours[]` grows from 24 to the 7-day horizon; the iOS decoder must **not assume any fixed length** (not 24, not 168 — read `hours.length` / `days.length`), and window indices can point a week out. The day-bucketed activity result is a new shape (replaces the single top-level window per activity). The **Daily Digest** must day-scope — slice day 0 before searching, or a Monday push reports Saturday's window; **Window Watch** (time-ranged) is unaffected. `findLongestWindow` is **reused unchanged** — it already iterates `ratings.length`; a thin **per-day bucketing layer** slices each local day's hours, calls it, and offsets the slice-relative result back to **global `hours[]` indices**. Other changes: a `FORECAST_HOURS` **ceiling** (168) capping the slice in `parse.js` — `slice(0, FORECAST_HOURS)` replaces `slice(0, 24)` and passes through fewer when the provider returns fewer — plus test-fixture churn (fixtures and assertions that hardcode `24`/`0..23`/`7` become variable, asserting against the actual returned count and contiguous `dayIndex`, never a magic number). Selecting the 7-day horizon also means pointing the Meteosource call at the `flexi` tier endpoint (`/api/v1/flexi/point`) instead of `/free/` (which caps at 24). Payload grows ~7× (further once air-quality + marine fields land), raising the value of the 30-minute location cache. The day-bucketed engine output keeps the activity-agnostic contract of [ADR-0002](0002-activity-agnostic-engine.md) — the engine still evaluates caller-supplied profiles; only its result shape gains the day dimension. New for calendar bucketing: the **response gains a top-level `timezone`** field (the location's IANA zone) so the client renders clock times and day labels in the *same* zone the server bucketed by; a **time-boundary module** owns `(utc hour, IANA zone) → localDay`. **Fetch wrinkle (Phase-1 detail):** the zone is only exposed by Meteosource under `timezone=auto`, which returns *local* timestamps — reconciling that with the UTC-`Z` `forecastStart` contract (convert in the adapter, or carry the zone alongside UTC) is settled at implementation time, not pinned here. **Landmine to encode in the module's contract:** local-day must be computed from a UTC *instant* (Z-suffixed); a bare `new Date("2026-06-19T12:00:00")` parses in the *server's* local tz and silently shifts every bucket on a non-UTC host.

**✅ Provider verification — Meteosource done (2026-06-19).** A live probe across Meteosource tier endpoints confirmed the `flexi` tier returns **~164 clean hourly entries** (no degradation to 3-hourly/daily — hourly throughout the horizon). This is why **168 is a ceiling, not a count**: the provider serves a fixed *horizon* from the current hour, so the exact entry count drifts (~160–168) with request time and the last day is partial. The `/free/` tier caps at 24 and is unusable for the 7-day view. **Still to verify when integrated:** the air-quality and marine sources must independently return clean *hourly* data across the same horizon — verify each at the point its adapter lands, not before.

Recorded because clients decode against the (up-to-168-entry) day-bucketed shape (reversible only with another contract bump), a future reader will ask why hours are flat on the wire but results are bucketed and why there is no week object, and it is the result of a real trade-off between flat-vs-bucketed search and nested-vs-derived grouping.
