# Forecast extends to 7 days; hours stay flat, evaluation is day-bucketed

The forecast horizon extends from 24 hours to a **7-day rolling window**, served as a flat `hours[]` addressed by `index` against `forecastStart`. **168 (7 × 24) is a ceiling, not a fixed count.** The horizon is **provider-determined**: `hours[]` carries however many clean hourly entries the provider actually returns, capped at 168 — fewer is valid. (Verified: Meteosource's `flexi` tier returns ~164 clean hourly entries; see verification note below.) The wire contract keeps **hours flat**: no nested day object. "Day" is **derived** (`floor(index / 24)` → `dayIndex` 0..6); because the count is not a multiple of 24, the **final day bucket may be partial** (e.g. 20 hours, not 24). The decision engine searches **per day**: each activity result becomes up to 7 day-results `{ dayIndex, rating, startIndex, endIndex, duration }` (or `rating: null` for a day with no qualifying window). The engine is **count-agnostic** — it searches whatever hours each bucket contains — so a partial final day needs no special handling. The system **never fabricates or interpolates** hours to reach a target count; that would resurrect the false-**Perfect** hazard the absent-data guard exists to prevent.

Chosen because extending the horizon unlocks the multi-day timeline drill-down (users want to check tomorrow / the week, not only react to push). But the existing single-best-window search assumed a 24-hour bucket: run unchanged over 168 hours and it fuses a Thursday-evening and Friday-morning block into a "30-hour Perfect window" no human treats as one outing, and it returns windows days away when the dashboard card wants *today*. Per-day bucketing maps to how people actually plan an outing and hands the timeline view its data for free.

The window is **rolling** — every request is a fresh day 0..6 relative to `forecastStart`; there is no accumulating day counter ("day 299" never arises). Any absolute calendar position is the **derived date** (`forecastStart + index → 2026-06-22`), never a day number.

Rejected alternatives: a nested `week { days: [...] }` object (carries no payload of its own — a box around seven boxes — and hardens a grouping the client may want to slice differently, e.g. "next 48 hours" spanning two days); an unbounded single-window search over all 168 hours (produces the non-physical cross-midnight windows above).

**Consequences:** the response is a versioned contract bump — `hours[]` grows from 24 to the 7-day horizon; the iOS decoder must **not assume any fixed length** (not 24, not 168 — read `hours.length` / `days.length`), and window indices can point a week out. The day-bucketed activity result is a new shape (replaces the single top-level window per activity). The **Daily Digest** must day-scope — slice day 0 before searching, or a Monday push reports Saturday's window; **Window Watch** (time-ranged) is unaffected. The engine core is **untouched** — `findLongestWindow` already iterates `ratings.length`; the change is a `FORECAST_HOURS` **ceiling** (168) capping the slice in `parse.js` — `slice(0, FORECAST_HOURS)` replaces `slice(0, 24)` and passes through fewer when the provider returns fewer — plus test-fixture churn (the fixtures and assertions that hardcode `24`/`0..23` become variable-length, asserting against the actual returned count rather than a magic number). Selecting the 7-day horizon also means pointing the Meteosource call at the `flexi` tier endpoint (`/api/v1/flexi/point`) instead of `/free/` (which caps at 24). Payload grows ~7× (further once air-quality + marine fields land), raising the value of the 30-minute location cache. The day-bucketed engine output keeps the activity-agnostic contract of [ADR-0002](0002-activity-agnostic-engine.md) — the engine still evaluates caller-supplied profiles; only its result shape gains the day dimension.

**✅ Provider verification — Meteosource done (2026-06-19).** A live probe across Meteosource tier endpoints confirmed the `flexi` tier returns **~164 clean hourly entries** (no degradation to 3-hourly/daily — hourly throughout the horizon). This is why **168 is a ceiling, not a count**: the provider serves a fixed *horizon* from the current hour, so the exact entry count drifts (~160–168) with request time and the last day is partial. The `/free/` tier caps at 24 and is unusable for the 7-day view. **Still to verify when integrated:** the air-quality and marine sources must independently return clean *hourly* data across the same horizon — verify each at the point its adapter lands, not before.

Recorded because clients decode against the (up-to-168-entry) day-bucketed shape (reversible only with another contract bump), a future reader will ask why hours are flat on the wire but results are bucketed and why there is no week object, and it is the result of a real trade-off between flat-vs-bucketed search and nested-vs-derived grouping.
