# Device-keyed server-side push evaluation

Push notifications (#6c digest, #6d Perfect-window detector) need Activities evaluated while the app isn't running — but [ADR-0002](0002-activity-agnostic-engine.md) made the engine hold no activity list, and [ADR-0001](0001-no-accounts-guest-first.md) cut accounts. Three architectures were weighed (grill, 2026-07-16):

- **Client-only** (BGAppRefreshTask + local notifications): zero backend state, but iOS schedules background refresh opportunistically — a morning digest can arrive hours late or never. Rejected on delivery reliability.
- **Silent-push wake + client eval**: server stores tokens only (privacy win), but silent pushes are throttled and silently droppable (Low Power Mode, force-quit) — the least reliable push path with the most moving parts. Rejected.
- **Server-eval, device-keyed** — **chosen.** The device registers an anonymous snapshot `{ apnsToken, home lat/lon, activities[] }` keyed by its Keychain install ID (the identity ADR-0001 anticipated); server crons evaluate with the existing engine and push.

The registration contract is a **full-snapshot upsert** (`PUT /api/v1/devices/:deviceId`, `DELETE` on opt-out): client-authoritative, last-write-wins, no merge logic — the client re-upserts on any change (activity edit, home change, APNs token refresh). Registration is **opt-in** (Settings toggle) and **requires a real location** — there is no fallback-location push. Snapshot Activities are validated with the same ADR-0005 rules as the rating body.

**Consequences.** The `/rating` path stays stateless; per-device state exists only on the push path — Railway **Postgres** joins the stack (`devices` + notification-state tables, Activities as JSONB, idempotent `initDb()`, no migration framework). Jobs run **in-process** (`node-cron`), so the web service must be always-on and **single-replica** (2+ replicas duplicate pushes — accepted constraint at this scale). APNs goes through the `apns2` package behind our own `src/notifications/` seam (provider-specifics stop at the boundary); the `.p8` key ships as env-var PEM content (Railway has no secret files). Product decisions riding this ADR: **Digest** at per-device local 6am (hourly cron pass + sent-today marker), covering today/tonight plus week-ahead Perfect highlights; **Detector** is Perfect-only, at most one alert per (device, activity, bucket), horizon limited to buckets 0–1 — a good→perfect upgrade alerts inherently as the bucket's first Perfect. Staleness is bounded by the upsert-on-change contract: a device that never re-syncs is pushed from its last snapshot.

Recorded because this reintroduces server-side per-device state into a deliberately stateless backend, and the rejected alternatives (client-only, silent-push) will look attractive again to anyone who hasn't seen the delivery-reliability trade-off. Supersedes the pre-rebuild #6c design (user-keyed, JWT, `selected_activity_ids`) and the old grill's "Daily Digest stays day-0" note — the digest now carries week-ahead Perfect highlights *because* the detector's horizon is capped at 48h.
